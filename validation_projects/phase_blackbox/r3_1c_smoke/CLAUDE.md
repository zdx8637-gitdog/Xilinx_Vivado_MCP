# Agent3 Instructions: R3.1-C Phase Black-Box Smoke

## Role and scope

- You are Agent3, using a fresh context for an independent black-box acceptance.
- This project is the B04 R3.1-C preconditioned public MCP smoke test.
- This is not B09 and does not verify the complete GPIO workflow.
- Do not modify production code, frozen tests, root `.mcp.json`, or Manager harness files.

## How MCP is used

- Do not configure or load `zynq_mcp` as a Claude Code MCP server for this test.
- Do not restart Claude Code for this test.
- `runner.py` starts its own `python -m mcps.zynq_mcp.server` subprocess through the MCP SDK stdio transport and calls public tools through `ClientSession`.
- Run the command from the repository root so the `mcps` package is importable.

Example:

```powershell
Set-Location D:\fpgaproject
python validation_projects\phase_blackbox\r3_1c_smoke\runner.py `
  --manifest <scenario_manifest.json> `
  --scenario all `
  --run-id <run-id>
```

The Manager Reviewer supplies `scenario_manifest.json`. This manifest declares the **effective expected** directory and the **approved evidence root**. The runner reads effective expected contracts from that directory — these are generated by the Manager-only `provision.py` from checked-in templates and contain no `PLACEHOLDER_*` values.

## Effective expected contracts

- Checked-in `expected_outputs/*.json` are **templates** — they may contain `PLACEHOLDER_SID`, `PLACEHOLDER_PROJ`, and `PLACEHOLDER_STAGE` markers.
- The Manager Reviewer runs `provision.py` which substitutes real values and writes **effective expected** JSON files under the manifest-declared `effective_expected_dir`.
- The runner **only** reads effective expected files. It validates their SHA256 against `manifest.effective_expected_shas` before any scenario execution.
- The runner does **not** modify or inject any `expect` values. Do **not** point `--expected-dir` at the checked-in templates.

If you pass `--evidence-base` or `--expected-dir`, they must equal the manifest-declared `approved_evidence_root` and `effective_expected_dir` respectively — otherwise the runner exits with an error.

## Preconditions and forbidden access

- There are **five independent runtime directories** (one per scenario), not four.
- The supplied runtimes are already preconditioned by the Manager Reviewer.
- Do not run `provision.py` or `verify_readiness.py` yourself.
- Observe the initial state only through public `get_session_info` and `get_execution_state` calls.
- Do not create, edit, read, or validate `execution_ledger.json`.
- Do not import internal `mcps.zynq_mcp` modules in test code or replace the runner with internal calls.
- Do not claim that the preconditioned setup covered the public `create_session` lifecycle. Report it as `PRECONDITION_OBSERVED`.
- If the manifest, receipt, or required fixture is missing, stop that scenario and report it as missing; do not repair the runtime.

## Scenarios

Run all five scenarios unless the Manager Reviewer explicitly requests one:

- `capabilities`: public tool count, PL tool presence, and input schema.
- `success`: `pl_generate_system_top`, terminal success, artifact SHA, and `PL_GENERATE -> PL_BUILD`.
- `missing_revision`: structured `PLATFORM_MANIFEST_NOT_FOUND` failure and cleanup.
- `wrong_stage`: admission rejection with `STAGE_PREREQUISITE_UNMET` and no operation.
- `invalid_schema`: integer, null, and object `wrapper_path` rejection with unchanged public state.

The effective expected JSON files are the acceptance contract. Every assertion must be evaluated and recorded with expected value, actual value, and PASS/FAIL. A mismatch is a test failure.

## Evidence and report

- Preserve the runner-generated evidence directory; do not overwrite an earlier run.
- Review `summary.json`, per-scenario result files, `responses/`, `state_traces/`, `operation_logs/`, and generated artifacts.
- Report the exact command, scenario counts, assertion counts, exit code, and any exception.
- Report the initial stage/lane/worker as `PRECONDITION_OBSERVED`.
- Do not report a software PASS as physical hardware acceptance.

No Vivado Worker, hw_server, JTAG, UART, board programming, or physical LED verification is part of R3.1-C. These are `NOT_APPLICABLE` for this project. Any later hardware result must be confirmed by the user.
