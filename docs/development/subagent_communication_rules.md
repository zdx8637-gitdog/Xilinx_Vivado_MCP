# 子代理通讯机制（长期纪律，跨所有 Brick 必读）

> 目的：与子代理（subagent）协作的**机制性实测结论**，与具体 Brick 无关。任何上下文压缩、会话恢复、goal 续轮之后**必读**（CLAUDE.md 概览区有指针，会话注入即见）。
> 来源：B13 期间实测定论（2026-09-01，「5 条排队消息事故」+「三选一提问处置」+「ACK/NAK 裁决直投」三轮实战总结）。
> 变更记录：v1 2026-09-01 初版。

## 1. send_message 语义：只排队，不打断

- `send_message` 把消息排为子代理的**下一回合**，**不打断正在运行的当前回合**；返回 "queued" 只代表入队成功，**不代表送达、更不代表执行**。
- 子代理回合未结束时连发多条 = 排队堆积（B13 曾堆到 5 条）。排队消息**无法删除**（父代理无此工具，人类侧同样删不掉），只能等它逐条消化。
- 子代理自己发起的提问（ask_user_question）与排队消息同性质：回合挂着时，任何投递都进队。

## 2. 方向级指令必须「中断 + 合并投递」

方向级变化（契约修订、平台/方案裁决、范围变更）不得用普通 send_message 逐条发送。标准动作：

1. `interrupt_agent` —— 停止当前回合（已完成的磁盘产物保留，不丢；只作废在途工作）；
2. `send_message` 一条**合并指令**（见 §6 五要素），明示"本条替代此前全部排队消息"。

反面教训（B13 实况）：不中断、逐条发 → 消息堆 5 条，子代理按旧口径空跑整轮，用户侧看到混乱队列。

### 2.1 注入新提示词的可靠协议（决策树，B13 两次事故实测定论）

- **纯引导（只发消息不打断）不可靠**：消息只排队、队列 FIFO 且不可删除；新提示词会被旧消息挡在后面（实证①：闭环消息在队尾，子代理先执行了过期的「恢复执行：继续 P1」；实证②：停用后残留队列仍驱动它跑完一整套平行收尾并覆盖了板卡）。
- **标准注入 = 中断后注入**：`interrupt_agent`（停当前回合，磁盘产物保留）→ `send_message` 一条合并指令（§6 五要素 + 跳过规则 + 回退触发）。保证：新提示词成为**下一回合**。
- **可靠边界（实测）**：中断+注入只保证「下一回合是我」，**不清除更早的积压**——过期指令在其后的回合仍会被执行。因此按队列状态选路：
  1. 队列基本干净（≤1-2 条无害消息）→ 中断 + 注入合并指令，可靠；
  2. 方向级变化且回合在跑 → 必须中断 + 合并投递，禁止纯引导；
  3. **队列已污染（≥3 条堆积，含过期方向指令：旧裁决/旧放行/旧恢复）→ 不要抢救**：该子代理永久停用（不再发任何消息，队列冻结零成本），新任务用**全新子代理**（新会话 = 干净队列，新提示词直接写进任务提示）。B13-P2 即采用此路。

## 3. 发出后必须跟进引导（不能发了就不管）

"queued" ≠ 送达。发出后必须确认投递落地：

- 用 `list_agents` 看状态快照：`running` = 回合未结束、消息还在队列里；`idle/ready` = 回合已结束、消息可投。
- 消息是方向级且子代理仍 `running` → 立即 `interrupt_agent` + 合并重发，不让它在旧口径上继续空跑。
- 最终以子代理 settle 后的**完成通知**（含最终消息）确认收到并执行。
- 此"跟进"不违反零轮询：零轮询禁的是等结果时的 busy-poll；裁决后确认投递是必须的主动动作。

## 4. 提问与决策点处置（硬性规则，2026-09-01 用户定）

- **子代理禁用 `ask_user_question`**：任何决策点、方案选择、需要人类输入的情形，一律**停止回合并把问题、自身倾向的方案与理由写进最终汇报**（随完成通知到主代理），等主代理裁决后 `send_message` 答复。主代理消息是权威指令源；人类**转贴主代理裁决文本**到答题卡视为有效答复（照执行），人类自行撰写的回复无效。
- 人类侧：**不自行作答**；把主代理的裁决/答复文本转贴到答题卡是有效通道（等价于主代理答复，B13 实证）。看到答题卡 → 转述主代理并等裁决文本，不要自己写答案。
- 派发新子代理时，任务提示必须明写「禁止使用 ask_user_question；决策点停止+汇报，等主代理答复」。
- 转述必须用**文字**：本 harness 无图像模型（deepseek-v4-pro / deepseek-v4-flash 均声明不支持图像输入，read_image 对任何代理都报错），截图内容任何代理都读不了。

## 5. 队列消息不可删除 → 跳过规则

合并指令必须附「队列处理规则」：旧消息若随后逐条投递，子代理逐条回复"已吸收于合并指令 vN，跳过"，**不重做其中的动作**；仅按原文落实收编不了的细节（例：B13 的 P0 两小项原文）。没有此规则时，旧消息会逐个触发空转回合。

## 6. 合并指令五要素

1. **版本号**（vN）与"本条替代此前全部排队消息"声明；
2. **覆盖清单**：逐条列出被收编的旧消息及各自落在本条的哪一节；
3. **重启口径**：第一步必做动作（如重读冻结文档），明确旧口径作废的边界；
4. **回退触发**：撞硬墙时停下来向主代理报告，不得自行切换方案；
5. **冲突升级条款**：本条与冻结文档冲突时停下来问，不得自行裁决。

## 7. 不变纪律（与本文档并列）

- **零轮询**：等完成通知，不 busy-poll 子代理；`list_agents` 只用于「裁决前确认状态」或「回答用户关于状态的直接提问」。
- **子代理禁用 ask_user_question**（§4 硬性规则）：决策点停止+汇报，等主代理答复；新派发任务提示必须写明此条。
- **串行执行**：修复 / EDA / 硬件相关的子代理同一时刻只跑一个。
- 子代理提问默认等人类转述；转述到后按 §4 裁决并直投。
