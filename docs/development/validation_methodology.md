# 验证方法论：三层白盒 + 绕行审计 + 黑盒终审（B13-P4 黑白盒复盘沉淀）

- 日期：2026-09-05
- 来源：B13-P4 白盒/黑盒差异复盘（白盒 8 项发现、黑盒 4 项 P1 + LESSONS_LEARNED、主代理逐项复核与三方讨论）
- 适用：此后所有 Brick 的白盒/黑盒任务书设计与验收审核。**本文件是模板级规范，任务书按附录模板生成。**

---

## 一、核心认知（为什么需要本规范）

黑白盒复盘得出的四个已被实证的判断：

1. **专家补偿效应**：白盒（连续体、有历史上下文）的先验知识会把 MCP 接口缺陷"吸收"掉——工具坏了，测试却绿了。绿的是"专家系统可用性"，红的是"产品可用性"。
2. **功能覆盖 ≠ 状态转换覆盖**：四个 P1（ps_load_hardware 映射 / PL 摘要不含 IP 产品 / PL 工程不注册 IP 仓库 / ps_mem_read 坏）全是"A→B 生命周期转移"的裂缝，不是单点功能坏。FPGA+Vivado+Vitis+JTAG+PS+PL 是高度有状态系统，缺陷藏在状态 A→状态 B，而不是状态 A。
3. **名义能力 vs 实际可用能力漂移**：MCP 的工具描述宣称"可用"，实际"某些状态/某些迭代下不可用"。白盒绕开时不觉得是问题（它把绕行当正确流程），文档面与专家实践面就此漂移。
4. **黑白盒差异 = 漂移量的量化**：黑盒按"说明书"走，每处漂移就是一场战斗——这正是黑盒 token 3× 的结构性来源，也是黑盒不可被替代的价值。

## 二、三层白盒模型（L1/L2/L3）

### L1 白盒功能验证（现状已较好）

单个工具本身正确性：参数校验、原子语义、fail-closed、回读校验。现有 1500+ 回归 + host_live 属此层。**L1 通过只证明"工具对"，不证明"串起来对"。**

### L2 白盒生命周期验证（本轮核心缺口）

定义 Zynq 生命周期状态机，白盒任务书必须要求**每个重要公共工具至少出现在一次跨状态场景**，且全走公开 MCP API：

```
Create ──► Build ──► Modify ──► Rebuild ──► Export ──► Reload ──► Program ──► Debug ──► Recover
(平台)    (PL/PS)   (改RTL/IP/BD/源)  (原地重建)  (XSA)    (导入PS)   (JTAG)    (读/查)   (异常恢复)
```

强制转移清单（白盒必做，缺一项即任务书不完整）：
- 打包用户 IP → 实例化 → **修改 IP 内容 → 原地重新打包 → 原地重建 PL**（不打散工程）——暴露摘要/注册类缺陷；
- 导出 XSA → **重导出字节一致** → 导入 PS → **重复导入幂等**；
- 部署**必须走 `ps_load_hardware`** 并验证 dow 映射（禁止默认跳过）；
- 内存观测**必须先用 `ps_mem_read`** 与手动 xsdb 对账（禁止直接绕手动路径）；
- 制造一次 FAILED 后同签名重试；制造一次中断/超时后走 recover；
- BD 修改 → validate → 回退（workflow_rollback）→ 再前进的完整环。

### L3 白盒伪黑盒验证（强制公共面）

白盒仍可用其知识**设计**验证方案，但执行时：
- 只允许使用 MCP 公开工具与 Skill 书面指引；
- **禁止**直接调用内部 Vivado Tcl / xsdb 脚本 / 历史部署配方替代 MCP 工具（诊断回退必须先声明并计入绕行审计）；
- 每个公开 API 至少一次正常路径 + 一次错误恢复路径。

**L3 的边界**：伪黑盒不能替代真黑盒——先验在认知层（解读错误信息、选择次优路径）无法被工具约束消除。L3 的目标是把黑盒才能发现的问题**提前暴露 ~80%**，不是取代终审。

## 三、白盒绕行审计（必填节，机械执行）

每轮白盒报告必须附 `tools/audit/bypass_audit.py` 输出，主代理复核。审计内容：

1. **工具使用矩阵**：109 工具 ×（调用次数 / 成功 / 失败）；
2. **未调用工具清单**：逐条标注「未涉及」或「已绕开」——**标注"已绕开"即视同 finding 上报**，需说明替代路径与理由；
3. **外部替代线索**：工作区内 xsdb/tcl/vivado batch 脚本及调用记录（替代了哪个 MCP 工具）；
4. **失败调用清单**：所有 error/FAILED/TIMED_OUT/INTERRUPTED/OUTCOME_UNKNOWN 调用——其中被经验 workaround 消化掉的，逐条登记"被吸收的错误"。

审计纪律：**不能因为测试方知道某条路有坑就主动绕开**——公开 API 必须故意使用并走完整流程，绕行只有两类合法理由：(a) 契约明确排除；(b) 已按本规范登记为 finding 并获主代理裁决。

## 四、黑盒定位与调度

- 黑盒 = 终审，不可被 L3 替代。全新无记忆、仅公开契约 + 板卡包 + Skill + MCP 自描述。
- **切片早跑**：黑盒按门禁切片分阶段派发（如 L1 链 → 三档 → 行为链），避免大爆炸式一次吞全链（大爆炸 = token 密度高 + 上下文易污染 + 交接成本）。
- 黑盒产物：LESSONS_LEARNED（现象→根因→对策）必须交回主代理，用于反哺 Skill 与修复轮——**黑盒发现的每一条经验都必须回流到 Skill 或工具描述，否则下个黑盒重付学费。**

## 五、任务书模板（附录）

白盒任务书必须包含以下节（缺一不可）：

1. 目标（产品链判据 + 框架机制清单）；
2. L1 范围（复用回归，注明新增）；
3. **L2 生命周期转移清单**（照 §二，逐项打勾）；
4. **L3 强制公共面规则** + 允许的诊断回退白名单；
5. **绕行审计义务**（报告必附 bypass_audit 输出 + 未调用工具逐条标注）；
6. 输入白名单（SHA 冻结）+ 隔离纪律；
7. 完成标准 + 停止汇报纪律（禁 ask_user_question、机器可验证据、硬件串行）。

黑盒任务书在既有模板（输入白名单/隔离/验收基准/规范）基础上追加：**切片定义**（哪几道门禁一批）与 **LESSONS_LEARNED 回流义务**。
